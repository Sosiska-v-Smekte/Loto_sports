## Продукт
Платформа помогает человеку перейти от «хочу заниматься, но не с кем» к конкретной совместной активности: понять, кто собирается, где, когда и как присоединиться. Это НЕ соцсеть, НЕ система соревнований и НЕ игра. Аудитория — люди с разным опытом (новички, любители, профи) и разным цифровым опытом, включая старшее поколение. Сервис универсален: футбол, шахматы, бег, зарядка во дворе и любые нишевые направления должны укладываться в одну логику.

- Frontend: React 18 + TypeScript + Vite, React Router, TanStack Query, Tailwind CSS (дизайн-токены через CSS-переменные), dayjs с локалью `ru`.

- Деплой: один Docker-образ, в котором FastAPI отдаёт API под `/api` и собранный фронтенд как статику; плюс `docker-compose.yml`. Локальный запуск без Docker тоже должен работать.

## Делаем ТОЛЬКО обязательный минимум из ТЗ
1. Три роли: обычный пользователь, организация/сообщество, администратор. Экраны входа и регистрации есть, но авторизация имитируется демо-аккаунтами.
2. Создание и публикация мероприятий от пользователя или допущенной организации; лента, поиск, фильтры, карточка мероприятия.
3. Каталог спортивных направлений + возможность указать своё направление. Новое направление НЕ требует правки кода.
4. Два режима записи на выбор организатора: «Свободная запись» и «По заявке» с подтверждением.
5. Организатор видит участников и заявки, принимает/отклоняет заявки; пользователь всегда видит понятный статус своей записи.
6. Текстовое обсуждение под мероприятием: любой пользователь задаёт вопрос, организатор отвечает, авторство различимо, ответ организатора визуально помечен.
7. Контур организации: представитель создаёт профиль организации и отправляет заявку на допуск; до одобрения видит статус заявки, но не может публиковать мероприятия и не имеет публичной страницы; после одобрения публикует события без повторной модерации.
8. Админка: просмотр и поиск организаций и мероприятий; одобрение/отклонение заявок организаций с причиной (причина видна организации); снятие с публикации или удаление мероприятия с причиной (видна организатору); скрытие отдельного сообщения в обсуждении с сохранением остального.

## Сущности и правила (это источник истины для бизнес-логики)

- **User**: id, name, email, password (демо, хранить хэш), avatar_url, city, about, `is_admin: bool`.
- **Organization**: id, owner_id → User, name, description, sports (текст или связь со Sport), city, contacts, `status: pending | approved | rejected`, rejection_reason, created_at, reviewed_at.
  - Один пользователь может быть владельцем организации. «Роль организации» = пользователь, у которого есть одобренная организация; он может создавать события от своего имени или от имени организации.
  - Публичная страница и публикация событий — только при `approved`.
- **Sport**: id, name, `is_custom: bool`, created_by → User | null. Базовый список заводится сидом (футбол, баскетбол, волейбол, теннис, настольный теннис, шахматы, бег, йога/зарядка, плавание, велоспорт). При создании события можно выбрать существующее направление или ввести своё: бэкенд нормализует название (trim, регистр, ё→е) и переиспользует уже существующее, иначе создаёт новое `is_custom=true`. Каждому направлению — цвет карточки и иллюстрация; для пользовательских направлений — детерминированный цвет из палитры по хэшу названия и нейтральная иконка.
- **Event**: id, title, description, sport_id, `organizer_user_id`, `organization_id | null` (если задан — событие от имени организации), starts_at, ends_at | null, city, address, place_details, level (`any | beginner | amateur | pro`, отображается как «Можно без опыта», «Для новичков», «Для игроков», «Для опытных»), requirements (подготовка/инвентарь, текст), `join_mode: open | approval`, `status: published | unpublished | deleted`, moderation_reason, created_at.
- **Participation**: id, event_id, user_id, `status: confirmed | pending | rejected`, created_at, decided_at. Уникальна пара (event_id, user_id).
- **Comment**: id, event_id, author_id → User, `is_organizer_reply` вычисляется (автор = организатор события или владелец организации-организатора), text, `is_hidden`, hidden_reason, created_at.

## Правила бизнес-логики (всё проверяется на бэкенде, фронт только отражает)
- Ленту и поиск видят только `published` события с датой в будущем (прошедшие можно показать отдельно, но не в основной выдаче).
- `open`: запись сразу создаёт `confirmed`. `approval`: создаёт `pending`; организатор переводит в `confirmed` или `rejected`. До подтверждения пользователь не участник.
- Организатор не может записаться на своё событие. Повторная запись запрещена (409).
- Принимать/отклонять заявки может только организатор события (для событий организации — её владелец). Админ НЕ рассматривает заявки участников.
- Создать событие от имени организации можно только если она `approved` и пользователь её владелец. Иначе 403.
- На `unpublished`/`deleted` событие нельзя записаться, в том числе по прямой ссылке и через API (409/403 с понятным текстом). Страница такого события по прямой ссылке показывает плашку «Мероприятие снято с публикации: <причина>» организатору и уже записавшимся; остальным — «Мероприятие недоступно». Существующие записи сохраняются, в «Моих активностях» у них статус «Мероприятие снято». Удалённое (`deleted`) — мягкое удаление, в выдаче не участвует нигде.
- Скрытое сообщение не показывается пользователям (вместо него «Сообщение скрыто модератором»), админ видит оригинал.
- Все действия администратора доступны только `is_admin`.
</domain_model>

## Имитация авторизации

1. пользователь создаёт событие со своим новым направлением → другой пользователь находит его в поиске и открывает;
2. новый пользователь создаёт организацию → она не может публиковать → админ отклоняет с причиной (видна) / одобряет → организация публикует событие → оно видно в ленте и на странице организации;

6. админ снимает событие → его нет в выдаче, запись по прямому запросу отклоняется, у записанного пользователя статус «снято».
Плюс тесты прав: чужой не может принять заявку, не-админ не может модерировать, `pending`-организация не может публиковать, скрытое сообщение не отдаётся пользователю. Проверка: `pytest` зелёный.
