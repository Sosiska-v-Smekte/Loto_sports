# Спортивный клуб — платформа совместных спортивных активностей

Прототип для финала хакатона ФСП (кейс Столото). Сервис помогает перейти от «хочу заниматься, но не с кем» к конкретной встрече: кто собирается, где, когда и как присоединиться. Подходит для любых направлений — от футбола и шахмат до зарядки во дворе и нишевых видов, которые пользователь добавляет сам.

**Для кого:** люди с любым спортивным опытом и разным цифровым опытом, включая старшее поколение. Поэтому в интерфейсе крупные кнопки и шрифт от 16px, у каждого статуса есть цвет, иконка и текст, а на каждом экране понятно, что произошло и что делать дальше.

Пошаговая проверка шести сценариев — в [docs/SCENARIOS.md](docs/SCENARIOS.md).

## Быстрый старт

### Через Docker (рекомендуется)

```bash
docker compose up --build
```

Откройте http://localhost:8000. При первом старте база и демо-данные создаются автоматически. Файл базы лежит в `./data/app.db` на хосте и переживает перезапуск контейнера.

Сбросить демо-данные: остановите контейнер, удалите `data/app.db` и запустите снова. Можно и так: `docker compose exec app python -m app.seed --reset`.

> **Обновились с предыдущей версии?** Схема базы изменилась: добавлены ответы на сообщения, скрытие записей и уведомления. Миграций нет, поэтому старую базу нужно пересоздать: `docker compose exec app python -m app.seed --reset`, а локально — `python -m app.seed --reset`.

### Локально, без Docker

Нужны Python 3.11+ и Node.js 20+.

```bash
# 1. Бэкенд
cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows; на macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python -m app.seed --reset      # необязательно: база и демо-данные создаются при первом старте сами
uvicorn app.main:app --port 8000

# 2. Фронтенд — в отдельном терминале
cd frontend
npm install
npm run dev                     # http://localhost:5173, запросы /api проксируются на :8000
```

Чтобы всё работало на одном порту, как в Docker, выполните `npm run build` во `frontend/`. FastAPI сам отдаёт `frontend/dist` по адресу http://localhost:8000.

## Навигация

- **Шапка (десктоп):** «Найти активность», «Мои активности», «Сообщества», у администратора ещё «Админка». Справа — «Создать активность», колокольчик уведомлений со счётчиком и меню аватара.
- **Меню аватара (☰ + аватар):** «Профиль» (ваш публичный профиль, там же кнопка «Редактировать»), «Мои активности», «Сменить аккаунт», «Выйти»; у администратора — «Админка».
- **Телефон:** нижний таб-бар «Найти», «Мои», «Создать», «Сообщества», «Уведомления» (с бейджем). Меню аватара — в шапке.
- **Организация** создаётся и управляется на странице «Сообщества»: кнопка «Создать организацию» или карточка «Моя организация» со статусом заявки. Старый адрес `/profile` ведёт на ваш публичный профиль.

## Специальные возможности

Кнопка с глазом в шапке открывает «Специальные возможности». Режимы включаются независимо и запоминаются на устройстве (localStorage):

- **Для слабовидящих** — высокий контраст, чёткие рамки вместо мягких теней, жирнее текст, подчёркнутые ссылки, двойная чёрно-жёлтая рамка фокуса, без фонового узора.
- **Для людей с нарушением цветовосприятия** — палитра по мотивам Okabe–Ito («хорошо» — синий, «плохо» — оранжевый), статусы дополнительно различаются рамкой (сплошная, пунктир, точки), выходные в ленте дат отмечены чертой.
- **Простой режим** — подсказка «как записаться» в три шага, кнопка «Подробнее и запись» на каждой карточке, выбор даты кнопками «Сегодня / Завтра / Другой день», все направления видны без прокрутки, полные подписи в меню, без анимаций.
- **Размер текста и кнопок** — обычный, крупный (×1,15), очень крупный (×1,3). При крупном тексте навигация переезжает в нижнюю панель, а карточек в ряду становится меньше.

## Роли и правила доступа

Все правила проверяются на бэкенде (`backend/app/services/`). Фронтенд только отражает их, поэтому прямой запрос к API их не обходит.

**Гость** видит ленту, поиск, карточки опубликованных мероприятий, страницы сообществ и профили организаторов. Чтобы записаться или написать в обсуждение, нужно войти.

**Пользователь**
- Регистрируется со строгой проверкой email и городом из справочника. Редактирует имя, город и «о себе» на своём публичном профиле.
- Создаёт мероприятия от своего имени, выбирает направление из каталога или вписывает своё. Название нормализуется (регистр, пробелы, ё→е), так что дубли не появляются.
- Выбирает режим записи: **«Свободная запись»** — участник подтверждается сразу; **«По заявке»** — организатор принимает или отклоняет. До подтверждения человек не участник.
- Записывается на чужие мероприятия: повторная запись (409) и запись на своё мероприятие (403) запрещены. Всегда видит статус: «Вы записаны», «Заявка на рассмотрении», «Заявка отклонена», «Мероприятие снято», «Мероприятие удалено».
- Убирает из «Моих активностей» неактуальные записи: отклонённые заявки и записи на снятые или удалённые мероприятия. Активные записи убрать нельзя (409). Запись скрывается только у самого пользователя: у организатора история заявок остаётся, а повторно подать отклонённую заявку нельзя.
- Как организатор видит в блоке «Управление» три вкладки: «Заявки», «Участники» и «Отклонённые». В состав участников и все счётчики попадают только подтверждённые. Админ заявки участников не рассматривает.
- Задаёт вопросы и отвечает на конкретные сообщения в обсуждении. Ответы показываются под исходным сообщением (один уровень вложенности), ответ на ответ — с упоминанием, кому отвечают. Сообщения организатора помечены меткой «Организатор».

**Организация** — пользователь с одобренной организацией.
- Организация создаётся на странице «Сообщества» («Создать организацию») и уходит администратору на проверку.
- Пока заявка на проверке или отклонена: публиковать от имени организации нельзя (403), публичной страницы нет. Статус и причину отказа владелец видит в карточке «Моя организация» в «Сообществах» и может отправить заявку повторно.
- После одобрения публикует мероприятия от имени организации без повторной модерации. Они появляются в ленте и на странице организации. Заявки на такие мероприятия рассматривает владелец организации.

**Модерация мероприятий — постфактум.** Предварительной модерации нет: мероприятие пользователя или одобренной организации публикуется сразу. Администратор контролирует контент после публикации — снимает мероприятие или удаляет его с причиной, которую видит организатор.

**Администратор**
- Просматривает и ищет организации и мероприятия; таблицы на десктопе, карточки на телефоне.
- Одобряет или отклоняет заявки организаций; причина отказа видна организации.
- Снимает мероприятие с публикации или удаляет его — всегда с причиной, которую видит организатор.
- Скрывает отдельное сообщение в обсуждении: остальные сообщения остаются, пользователи видят «Сообщение скрыто модератором», админ — оригинал и причину.

**Что происходит со снятым мероприятием**
- Пропадает из ленты, поиска, баннера и страниц организатора и организации.
- Записаться нельзя ни через кнопку, ни прямым запросом: API отвечает 409 «Мероприятие снято с публикации…».
- Существующие записи сохраняются. Записавшиеся получают уведомление «Мероприятие снято: причина», а в «Моих активностях» видят статус «Мероприятие снято» и причину.
- По прямой ссылке организатор, записавшиеся и админ видят плашку «Мероприятие снято с публикации: причина», остальные — «Мероприятие недоступно».
- Удалённое мероприятие (мягкое удаление) не показывается в ленте, поиске и по ссылке. У тех, кто был записан, в «Моих активностях» остаётся строка «Мероприятие удалено» с причиной и без ссылки, чтобы было понятно, что произошло; её можно убрать из списка. Администратор видит удалённые в списке с фильтром «Удалены».

В основной выдаче только опубликованные мероприятия, которые ещё не начались.

## Уведомления

Только внутри приложения, без email, SMS и push. В шапке колокольчик со счётчиком непрочитанных и выпадающим списком; на телефоне — пункт «Уведомления» в таб-баре и страница `/notifications`. Клик по уведомлению помечает его прочитанным и открывает нужный экран; есть кнопка «Прочитать все». Счётчик обновляется после действий пользователя и раз в 30 секунд.

| Когда | Кому |
|---|---|
| До начала опубликованного мероприятия меньше суток | Подтверждённым участникам и организатору |
| Кто-то ответил на ваше сообщение | Автору сообщения (на свой же ответ — нет) |
| Организатор принял или отклонил заявку | Автору заявки |
| Поступила новая заявка организации | Всем администраторам |
| Администратор одобрил или отклонил организацию | Владельцу (с причиной отказа) |
| Администратор снял мероприятие | Записавшимся и подавшим заявку |

Уведомления создаются в сервисном слое в момент события. Напоминания создаются «лениво» — при запросе списка или счётчика, поэтому фоновые задачи не нужны. Повторов нет: у каждого уведомления уникальный ключ.

## Справочник городов и проверка данных

- Города — только из справочника `backend/app/data/cities.json` (158 городов России), отдаётся через `GET /api/cities`. На фронте — выпадающий список с поиском в регистрации, профиле, создании мероприятия и организации и в фильтре на главной. Бэкенд проверяет город везде, где он принимается; на неизвестный город отвечает 422 «Выберите город из списка».
- Email проверяется на фронте и на бэкенде (`EmailStr` из Pydantic через `email-validator`, без DNS-запросов, только латиница в адресе). На некорректный адрес бэкенд отвечает «Введите корректный email». Email уникален и для входа без учёта регистра.

## Что имитируется

- **Авторизация.** Вход по email и паролю (пароли хранятся как PBKDF2-хэш) выдаёт случайный токен, он хранится в таблице сессий и передаётся в заголовке `Authorization: Bearer`. Нет подтверждения почты, восстановления пароля и OAuth. Регистрация реально создаёт пользователя.
- **Проверка организаций.** Администратор принимает решение вручную, документы не загружаются.
- **Данные.** Демо-сид: 8 пользователей, 3 организации (одобрена, на проверке, отклонена), 11 направлений (одно пользовательское), 21 мероприятие (17 в Москве, 3 в Санкт-Петербурге, одно снятое), заявки, обсуждения с ответами и уведомления у демо-аккаунтов.

## Известные ограничения

- Таблицы создаются при старте (`create_all`), миграций нет. Если модель поменялась, базу нужно пересоздать (`python -m app.seed --reset`).
- Время хранится без часового пояса как местное время сервера. В Docker задано `TZ=Europe/Moscow`.
- 3D-иллюстраций направлений нет, вместо них крупные эмодзи. В Windows они выглядят объёмно (Fluent), на других системах — плоско.
- SQLite рассчитан на одного пользователя-демонстратора. Для продакшена понадобятся PostgreSQL и миграции (Alembic).
- После любого действия фронтенд перезапрашивает все данные. Это просто и надёжно, но не оптимально на больших объёмах.
- Уведомления приходят опросом раз в 30 секунд, без websockets. Напоминание появляется, когда пользователь откроет приложение в последние сутки перед началом.
- Справочник городов статичный, правится в `cities.json`. Произвольный город указать нельзя.
